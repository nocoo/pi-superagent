# 005 CLI

The command line is the agent's **primary surface**. There is no web panel, so everything a supervisor needs to know
must be answerable here: whether anything needs them, whether the system is healthy, and the full history of one piece
of work from Trigger through Eval to Ticket. This document builds on [004 Prompts](004-prompts.md).

The design follows two things: this project's own principle that a surface shows only what needs a person
([000](000-philosophy.md)), and the conventions of the Herdr CLI — one place per concept, machine-readable output and
error codes, and no command that changes state without saying what it changed.

## Shape

```
pi-superagent [--state-dir DIR] [--json] <command> [<subcommand>] [args] [flags]
```

A group on its own prints that group's commands and exits 0. The program on its own prints global help and exits 0.
`--help` / `-h` works at every level.

| Command | Concept ([001](001-domain.md)) | Answers |
| --- | --- | --- |
| `status` | the whole system | Does anything need me now? Is it healthy? |
| `source` | Source | Is data arriving, and from where? |
| `thread` | Thread, Trigger | What happened in this conversation? |
| `trigger` | Trigger | Where did this one event go? |
| `decision` | Decision | Why was this accepted or refused? |
| `ticket` | Ticket, Assignment | What is being worked on, and how far has it gone? |
| `config` | Policy, deployment | What are the rules, and what is this instance? |
| `run` | — | Start the agent. |

Six read commands mirror the six domain concepts the original panel showed. There is deliberately **no** `worker`,
`queue` or `outbox` command: those are not concepts, they are how a Ticket or the system is doing. A worker appears in
`ticket read`, the effect queue and the outbox appear as health lines in `status`, and waiting Inputs appear in
`ticket show`.

## Conventions

### State directory

`--state-dir` > `$PI_SUPERAGENT_STATE_DIR` > `~/.pi-superagent/state`.

A read command **never creates it**. A missing directory is `no_instance`, not an empty healthy instance; reporting
plausible defaults for a typo is worse than failing.

### Output

Human by default: aligned, quiet, to **stdout**. `--json` prints `{"command": "ticket list", "result": …}`.

Diagnostics, progress and every log line go to **stderr**, always. `pi-superagent ticket list --json | jq` is safe
without redirecting anything.

A healthy part takes one line. A part that needs a person gets one row per item and nothing else.

### Exit codes

| Code | Means |
| --- | --- |
| 0 | success |
| 1 | a runtime error, or `status --check` finding work that needs a person |
| 2 | a usage error: unknown command, unknown flag, missing required argument |

The split follows Herdr: a script must be able to tell "your invocation is wrong" from "the invocation was fine and the
answer is no".

### Errors

Human: one line prefixed `pi-superagent:`, then an indented hint naming the command that fixes it, when one exists.

```
$ pi-superagent ticket show c5d4
pi-superagent: no instance at /Users/nocoo/.pi-superagent/state
  start one with: pi-superagent run
```

`--json`: `{"command": …, "error": {"code": …, "message": …}}` on stderr.

| Code | Means | Fix |
| --- | --- | --- |
| `usage` | the invocation is wrong | the hint line |
| `no_instance` | no state directory there | `run` once, or correct `--state-dir` |
| `not_configured` | the instance exists but has no deployment | `config set --repository …` |
| `not_found` | no such thread, trigger, decision or ticket | `… list` |
| `ambiguous_id` | a prefix matches several records | the candidates are listed |
| `locked` | another process holds the state directory | stop it first |

### Identifiers

A record answers to any unambiguous prefix of at least four characters. Human output shows eight. `--json` always
shows the full identifier. Identifiers are opaque: nothing derives meaning from their order or shape.

### Waiting

A command that could race a running agent accepts `--wait`, `--until <state>` and `--timeout <ms>`. It watches state
changes rather than polling, and it never retries a mutation whose effect is unknown.

## Reading the whole system

### `status`

Answers the first two questions, in this order.

```
$ pi-superagent status
needs a person (2)
  review   c5d4db13  Fix --prepare default wording          pull #7
  answer   7a1f0c92  Which module should this live in        "cli.ts or config.ts?"

system
  github   ready    12 notifications · 43 triggers / 24h · polled 41s ago
  workers  ready    1 running of 3
  queue    ready    nothing waiting
  outbox   ready    nothing pending
  evals    ready    nothing unavailable

policy 9fbbf9a0 · accept auto · 2 rules · 1 allowed login
```

The first block is grouped by the Ticket stages of [003](003-execution.md#ticket-stages), because the first question is
always "which of these waits for me". A ticket's row says **whom it waits for and what it needs**, never an internal
status code.

`--check` exits 1 when the first block is not empty. Without it, `status` always exits 0 — a command named `status` that
fails for an ordinary answer would be a trap.

`--json` returns the same facts as data.

### `source`

```
$ pi-superagent source
github   enabled   ready   43 triggers / 24h · polled 41s ago
                   nocoo/pi-superagent as @nocoo · observes issues, comments
                   filtered 7 · dropped 0
```

One block per configured Source. A Source that is off, stalled or failing says so in its detail line, and the counts
cover the same 24-hour window `status` uses so the two never disagree.

`--json` adds the raw health entry and the read cursor.

## Following one piece of work

### `thread list` / `thread show <thread>`

```
$ pi-superagent thread list --subscribed
THREAD       TRIGGERS  LAST              SUBSCRIBED  EVALUATING
github:6     4         2 minutes ago     1 ticket    no
github:5     2         1 hour ago        —           no
```

```
$ pi-superagent thread show github:6
#6 Fix the usage text                                  github:6
subscribed by c5d4db13 · nothing evaluating

  01:12:15  nocoo   The usage text says --prepare defaults to git worktree…
            → fanned out to c5d4db13 · accepted
  01:12:51  nocoo   Got it — the usage line will state…
            → delivered to c5d4db13, no Eval
  01:14:02  nocoo   Ship it
            → queued for Eval
```

Triggers in time order, each with its actor, a one-line preview, and its **disposition** — filtered, fanned out to which
tickets, delivered without an Eval, or queued. The disposition is what makes the system's behaviour legible, so it is
never hidden ([001](001-domain.md) calls it the record of a Trigger being filtered, evaluated or fanned out).

### `trigger show <trigger>`

The whole of one Trigger: source, threads, actor, whether it was human and whether it addressed the agent, the full
text, its channel address and URL, the Source's own metadata, and the disposition record.

This is what a Decision points at when its reason says no rule matched.

### `decision list` / `decision show <id>`

```
$ pi-superagent decision list --since 24h
WHEN      THREAD      KIND     WHY
01:12:40  github:6    accept   1 rule matched
01:11:02  github:4    ignore   no rule matched
```

```
$ pi-superagent decision show 436f3675
accept · inferred · policy 9fbbf9a0
thread github:6 · ticket c5d4db13

why      1 rule matched
rules    copy ✓  Author reports a spelling typo and states the exact correction

direction
         implementation requested   true
         target                     specified
         open decision              false
         evidence                   "It should read \"takes\"."

ticket   c5d4db13  Fix typo "takse" → "takes"
         scope — Correct the misspelling in the first line of the README.
```

The `direction` block is the part that decides whether a discussion is a request, so showing it turns "why did it
ignore me" into a fact ([004](004-prompts.md#the-three-facts)).

A candidate assessed but not accepted in `observe` mode reads `ignore` with a `would accept` line and the proposed title
and scope — exactly what an operator reviews before switching the accept mode
([002](002-authorization.md#accept-mode-and-rules)).

### `ticket list` / `ticket show <id>` / `ticket read <id>`

```
$ pi-superagent ticket list
person / review (1)
  c5d4db13  Fix --prepare default wording              ready · pull #7
working (1)
  8b2e1044  Improve the status output                  running, 3 minutes
idle (0)
ended today (3)
```

```
$ pi-superagent ticket show c5d4db13
Fix --prepare default wording                          c5d4db13
person / review · ready · pull #7

mandate   inferred · policy 9fbbf9a0 · rule copy
scope     Correct the misspelling in the first line of the README.
basis     admission · listedUnaddressed · observation auto

assignments
  01:12:44  running → ended   ready   The fix is limited to one usage line…

inputs
  01:12:15  trigger 02ba12d1  read
  01:12:51  trigger 23644adc  read

follows   github:6 (own, open)
channels  github #6
```

The mandate block is the answer to "may it do this": strength, the policy version it was accepted under, the rules it
matched, its scope, and how the gate admitted the Trigger ([002](002-authorization.md)).

`ticket read` prints the worker's own conversation, the only way to see what an agent actually did:

```
$ pi-superagent ticket read c5d4db13 --lines 40
  user        The usage text says --prepare defaults to git worktree, but…
  bash        rg -n "prepare" src/cli.ts src/policy.ts
  bash        git log -S"takse" -- README.md
  report      dropped — 全文检索无命中，无需改动
```

Tool calls are shown by name with their arguments truncated; assistant text is shown in full. `--follow` streams until
the assignment ends.

`ticket wait <id> --until person|idle|ended` blocks until the stage changes, for scripts that create work and want the
result.

## Configuring

### `config show`

```
$ pi-superagent config show
repository   nocoo/pi-superagent
account      @nocoo via gh
state        /Users/nocoo/.pi-superagent/state

policy       9fbbf9a0 · accept auto · 2 rules · 1 allowed login
rules        copy ✓   Explicit requests to correct a typo…
             visual ✓ Explicit implementation requests for local spacing…

eval         timeout 180s · model magpie/group/coding
executor     model magpie/group/coding · 3 workers
             prepare  git -C /srv/repo worktree add "$PI_SUPERAGENT_DIR" …
```

The rules, the admission table, the bot list and the Source configuration are too large for a line, so `config show
--json` prints the stored settings verbatim.

### `config set`

```
pi-superagent config set [--repository OWNER/NAME] [--allowed LOGIN]... [--add-allowed LOGIN]...
                         [--remove-allowed LOGIN]... [--mode off|observe|auto]
                         [--model ROUTE] [--assess-model ROUTE] [--max-workers N] [--prepare COMMAND]
                         [--pause|--resume] [--dry-run] [--yes]
```

Every write prints what changed and nothing else:

```
$ pi-superagent config set --add-allowed bob
allowed  nocoo      →  nocoo, bob
policy   9fbbf9a0   →  4c1e77b2
written
```

`--allowed` replaces the whole list and therefore **removes** every login it does not name. It refuses without `--yes`
and lists what it would remove first; `--add-allowed` and `--remove-allowed` change one entry without that risk.

`--dry-run` prints the diff and writes nothing.

A change to rules, the accept mode or a Source's Policy produces a new policy version, which `config set` reports,
because that version is what every live Ticket's mandate records ([002](002-authorization.md#policy-version)).

### `config edit`

Opens the stored settings in `$EDITOR` for the parts flags cannot express: the rule list, the admission table, the bot
list, a Source's configuration. On save it validates, writes nothing if the entry is invalid and reports the parse
error, then prints the same diff `config set` does.

### `run`

```
pi-superagent run [--verbose]
```

Refuses to start an instance with no deployment and names the command that configures one. Logs to stderr;
`--verbose` adds every domain event. Handles `SIGINT`/`SIGTERM` by stopping the workers and closing the store; a second
signal exits immediately. Runs until signalled — no timer bounds its lifetime.

## Not in the CLI

**Intervening in work.** Accept, stop, retry, attach and answer belong to the agent and to people through the threads
they are already in. The CLI reports; it does not do the agent's job. The one exception is `config set`, which is the
operator's own authority over the Policy.

**Rewriting history.** A Trigger is immutable and a Decision records what was true under its policy version. Nothing
rewrites either; correcting a wrong decision means a new request on the thread.

## Open questions

1. `status --check` exiting 1: useful for monitors, but a non-zero exit from a command named `status` may surprise.
   Currently it needs the flag, so the surprise is opt-in.
2. Rules are the most important thing to inspect and the hardest to edit as flags. `config edit` is the current answer;
   whether the rule list needs `config rule add|disable|rm` is unresolved.
3. `ticket read --follow` is a long-lived process with its own signalling. Worth having, but it lands after the read
   commands.
